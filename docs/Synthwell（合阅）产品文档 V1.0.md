### 1. 产品定义

#### 1.1 一句话定位（修正后）

**Reading Brain是一个Obsidian插件，为功利性阅读者提供"阅读→标注→AI理解→知识关联"的闭环，让PDF/电子书的阅读笔记自动生长为可检索、可关联的知识网络。**

> ⚠️ 修正说明：V0.1未区分"功利性阅读"与"休闲阅读"。红方Q23质疑用户是否愿意在Obsidian中读书；蓝方接受并修正——聚焦非虚构/学术/技术阅读（本身就是工作模式），排除小说/散文等休闲阅读。论据：Obsidian Annotator 8万+安装量证明用户确实在Obsidian中读PDF。

#### 1.2 产品愿景

到2029年，Reading Brain成为Obsidian生态中**功利性阅读场景**的首选插件——全球3,000-8,000月活用户，覆盖PDF/EPUB两类输入源，每位用户的知识库中平均有100+篇结构化读书笔记。Reading Brain不替代微信读书/Kindle的休闲阅读体验，而是成为它们的**知识层**——无论在哪里读书，笔记最终汇入Obsidian，由AI帮你理解、关联和检索。

> ⚠️ 修正说明：V0.1愿景（50,000月活）过于乐观。经红方Q5/Q7质疑后，采用区间估计而非伪精确数字。

#### 1.3 目标用户画像（修正后）

**主要用户（80-85%）：Obsidian重度用户 × 功利性阅读者**

- 25-40岁知识工作者（产品经理、工程师、咨询顾问、独立研究者）
- 每月读2-5本非虚构/技术/商业类书籍，有做笔记习惯但"记了就忘"
- 使用Obsidian 6个月以上，安装5+插件，理解双向链接价值
- 技术素养中高，但"配置API Key"仍是明确门槛（⚠️需spike验证）
- **排除**：Readwise/Zotero/NotebookLM的现有重度用户（错位竞争，红方Q19）

**次要用户（10-15%）：学术研究者 × Zotero-Obsidian双栈用户**

- 硕博研究生、高校教师、独立研究者
- 在Zotero中管理文献和初步标注，通过Zotero→Obsidian已有插件导入笔记
- 在Obsidian中用Reading Brain做**跨论文的AI分析和语义检索**（不替代Zotero的文献管理）
- 对本地数据存储有强偏好

> 🔴 修正说明：V0.1学术用户占比30%，红方Q4质疑后被完全接受——Zotero生态锁定效应极强，Reading Brain不替代Zotero，只做增强层。

### 2. 市场分析（修正后）

#### 2.1 市场规模（区间估计）

> ⚠️ 修正说明：V0.1给出伪精确的"11,400月活"，红方Q5完全击中——"猜测×猜测×猜测"。终版改用**区间估计+基准对比**。

**TAM（总可触达市场）**：全球Obsidian用户

- Obsidian全球MAU：200-300万（2025年估计，来源：官方Discord 17万+成员、论坛活跃度推算）
- 中国区占比估计：10-15% → **中国MAU 20-45万**（宽区间，承认不确定性）

**SAM（可服务市场）**：有系统化阅读+笔记需求的Obsidian用户

- 全球：200-300万 × 10-15% = **20-45万人**
- 中国：20-45万 × 10-15% = **2-7万人**

**SOM（可获得市场）**：实际可转化的月活用户

- 基准：Obsidian Annotator（PDF标注插件）安装量约8万+，说明"Obsidian内PDF阅读"需求真实存在
- 保守估计：全球月活 **3,000-8,000人**，中国月活 **1,000-3,000人**
- 依据：中等偏上Obsidian插件的安装→月活转化率通常为5-15%

> ⚠️ 这不是VC级别的市场。但¥68-88买断 × 5%付费 × 5,000月活 = ¥17,000-35,000/年，加上GitHub Sponsors，对个人副业可持续。

#### 2.3 差异化定位（修正后）

Reading Brain占据一个**独特的交叉点**：

```
// 代码块
                    数据本地化
                        ▲
                        │
            Reading Brain ●
                        │
   AI能力强 ◄───────────┼──────────► Obsidian原生集成
                        │
                ● NotebookLM
                        │
                        ▼
                    云端服务
```

**核心差异化**（三方盲评共识+红蓝对抗验证）：

1. **Obsidian深度集成**：笔记自动参与双向链接、Graph View、搜索、Dataview查询——云服务竞品无法复制这种集成深度（Tech机会#1，✅已验证）
2. **100%本地数据主权**：所有数据为Markdown文件，无服务器成本、无网络延迟、离线可用、永久可用（Tech+User共识，✅已验证）
3. **中文阅读体验优化**：针对中文PDF排版、CJK文本选择、学术论文格式做专项优化（PM机会#1，⚠️需spike验证）

**非差异化（不应宣传的）**：

- "功能最全"——这是"60分陷阱"（PM警告，✅已验证）
- "免费替代Readwise"——价格竞争不可持续
- "比NotebookLM更聪明"——AI能力依赖上游模型，插件层无法超越

#### 2.4 进入时机

**时机偏正面**：

1. AI阅读工具市场正在增长，NotebookLM的爆发验证了需求（2025-2026年）
2. Obsidian社区对"整合式阅读插件"有明确呼声（Annotator Issues中大量"加AI功能"请求）
3. DeepSeek等国内AI服务商降低了中国用户的API接入门槛
4. 现有阅读相关插件各自独立，尚未出现整合者

**时机风险**：

- Obsidian官方可能增强内置PDF阅读器（Tech风险#3，概率低但影响大）
- Readwise可能加深Obsidian集成（已有成熟插件）

> ⚠️ 应对策略：做深度而非广度——官方做基础的，我们做专业的。类比：VS Code有内置Git，GitLens仍有百万用户。

### 3. 功能清单（P0/P1/P2）

> ⚠️ 修正说明：V0.1的P0包含URL剪藏，经红蓝对抗后三方共识**砍掉**；导入功能从"附属"提升为"核心"；EPUB从P0移到P1。

#### P0：MVP必须（8-10周）

##### F1: PDF阅读器视图

- **用户故事**：作为一名经常读行业报告的产品经理，我想要在Obsidian中直接打开和阅读PDF文件，以便我不需要在PDF阅读器和Obsidian之间来回切换。
- **验收标准**：
  - 200页PDF打开时间<3秒（虚拟滚动，只渲染可视区域±2页）
  - 800页PDF不崩溃（内存占用<500MB）
  - 翻页帧率>30fps，无可感知卡顿
  - 支持目录面板跳转
  - 支持暗色模式（CSS反转处理）
  - 记住上次阅读进度（frontmatter存储页码）
  - 支持Ctrl+F文档内搜索（不与Obsidian全局搜索冲突）
  - **达标线修正**：≥Obsidian内置PDF查看器体验 + 高亮/AI增量（非macOS Preview的70%，红方Q8）
- **工作量**：15个工作日（占MVP 40%+，PDF是成败关键）
- **技术方案**：`pdfjs-dist@4.x` + Canvas + TextLayer + 虚拟滚动（IntersectionObserver）
- **论证状态**：⚠️需spike验证——W1必须完成PDF.js spike，若体验低于"可接受"线则项目转型
- **红方质疑**：Q8（PDF体验是否达标）、Q11（CJK文本偏差<10px——已从<5px修正）

##### F2: 高亮标注与笔记提取

- **用户故事**：作为一名读书做笔记的用户，我想要在PDF阅读时选中文字并创建高亮标注，以便这些标注自动变成Obsidian的Markdown笔记。
- **验收标准**：
  - 选中文本→弹出高亮菜单（4种高亮颜色）
  - 高亮可添加批注文字
  - 高亮数据持久化为JSON（按书籍hash存储，不修改原PDF）
  - 一键导出所有高亮为Markdown笔记，含书名/章节/页码元数据
  - 自动插入`[[书名]]`双向链接
  - CJK文本高亮偏差<10px（标准PDF：Word/WPS/LaTeX导出）
  - 竖排文本/扫描OCR PDF标注为"实验性支持"
- **工作量**：7个工作日
- **技术方案**：自定义TextLayer上的AnnotationLayer，坐标归一化到PDF页面坐标系
- **论证状态**：⚠️需spike验证——CJK文本选择精度需W1-W2实测
- **红方质疑**：Q11（CJK偏差极难实现→偏差标准修正为<10px+实验性标注）

##### F3: AI对话面板

- **用户故事**：作为一名阅读复杂文献的用户，我想要在阅读PDF的同时在侧边栏与AI对话，以便即时提问并让回答自动保存。
- **验收标准**：
  - 侧边栏View，与PDF阅读器左右并排
  - 支持选中PDF文字→右键"Ask AI about this"
  - AI回答用Obsidian MarkdownRenderer渲染，流式输出（SSE）
  - **MVP定位修正**："当前段落助教"——注入当前页±N页原文作为上下文，不做全书级分析（红方Q12）
  - 对话历史持久化为Markdown文件
  - 支持中断生成（AbortController）
- **工作量**：8个工作日
- **技术方案**：`fetch` + SSE手动解析，`LLMProvider`接口抽象（OpenAI兼容+DeepSeek+Ollama）
- **论证状态**：✅已验证——技术完全可行，Obsidian无CORS限制
- **红方质疑**：Q12（300页书上下文管理→MVP降低期望为段落级助教，全书分析是P1）

##### F4: Settings与配置面板

- **用户故事**：作为一名首次使用的用户，我想要在5分钟内完成配置并看到AI功能正常工作。
- **验收标准**：
  - 3步引导：选择AI服务商→粘贴API Key→连接测试
  - 支持3个Provider：OpenAI兼容、DeepSeek、Ollama
  - API Key加密存储（Electron `safeStorage`）
  - 一键连接测试
  - **费用预估器修正**：按用户选定的具体模型分别显示（非笼统"X-Y元"）；显示"本月已消耗tokens/预估费用"实时计数器（红方Q29）
  - 笔记存储路径配置
- **工作量**：3个工作日
- **论证状态**：✅已验证
- **红方质疑**：Q25（API Key门槛→应对：核心功能无Key也可用，AI为可选增强）

##### F5: 微信读书/Kindle笔记导入 ⬆️优先级提升

- **用户故事**：作为一名在微信读书上积累了大量高亮的用户，我想要把已有笔记导入Obsidian，以便知识库不用从零开始。
- **验收标准**：
  - 支持粘贴微信读书"全部笔记"导出文本（含多本书），自动按书名拆分
  - 支持Kindle `My Clippings.txt`导入
  - 支持微信读书网页版（weread.qq.com）HTML导出解析
  - 解析结果含：书名、作者、高亮文本、个人批注、章节/位置信息
  - 导入后笔记格式与F2高亮导出一致
  - 重复导入自动去重（基于高亮文本hash）
  - 解析后展示预览让用户确认（非静默导入）
- **工作量**：5个工作日（从0.5周提升到1周，红方Q26）
- **技术方案**：宽松正则解析 + 模板生成Markdown + 预览确认UI
- **论证状态**：⚠️需spike验证——导入20本书全流程耗时需实测
- **红方质疑**：Q24（冷启动问题→导入是解决冷启动的核心手段）、Q26（手动导入体验被美化→增加批量导入+预览确认）

##### F6: 数据schema v1定义

- **验收标准**：frontmatter字段、高亮JSON格式、阅读进度结构，含版本号`schemaVersion: 1`
- **工作量**：1个工作日（与W1基础设施并行）
- **论证状态**：✅已验证

#### 5.3 性能策略（含向量索引分片方案）

| 策略 | 解决的问题 | 实现方式 | 优先级 |
| --- | --- | --- | --- |
| **虚拟滚动** | PDF大文件内存爆炸 | IntersectionObserver，只渲染可见页±2页，销毁远离页面的Canvas | P0必须 |
| **Worker分离** | PDF解析阻塞主线程 | pdfjs-dist Worker独立文件加载，文本提取在Worker中完成 | P0必须 |
| **惰性加载** | 插件启动拖慢Obsidian | 向量索引、EPUB引擎按需加载，不在`onload()`中初始化 | P0必须 |
| **请求中断** | AI调用卡住影响体验 | AbortController，用户可随时中断AI生成 | P0必须 |
| **向量分片+懒加载** | 大Vault向量索引占内存 | 按书/文件夹分片存储，搜索时只加载相关分片，常驻内存<50MB | P1 |
| **低维向量模式** | 8GB设备内存紧张 | 支持256/512维embedding（vs默认1536维），内存开销降至1/3-1/6 | P1 |
| **增量索引** | 向量重建耗时 | 文件变更事件监听+脏标记，只重新索引修改的文件 | P1 |
| **设备检测提示** | 用户不知设备是否达标 | Settings中Vault>1000篇笔记时建议16GB+内存 | P1 |

> ⚠️ 修正说明：红方Q9质疑向量索引内存占用。终版增加分片+懒加载+低维模式三重策略。

#### 5.5 Plan B（PDF spike失败时的转型方案）

**触发条件**：W1 spike后，PDF.js在Obsidian中的阅读体验低于"可接受"线（200页PDF打开>5秒、滚动明显卡顿、CJK选区偏差>20px）

**转型方案**：

1. **砍掉PDF阅读器**：不再内嵌PDF.js，改为"纯笔记增强插件"
2. **核心功能转型**：
  - 高亮提取→保留：用户在外部阅读器（Preview/PDF Expert）中高亮后，通过导入功能提取到Obsidian
  - AI对话→保留：基于用户导入的笔记/剪藏内容做AI问答（不依赖PDF阅读器上下文）
  - 微信读书/Kindle导入→升级为最核心的功能
  - 跨书检索→保留：基于导入的笔记做向量索引和语义搜索
3. **新定位**："智能笔记导入+AI增强"插件，而非"Obsidian内阅读器"
4. **影响**：差异化从"阅读闭环"降级为"笔记增强"，但仍有价值（Annotator+Copilot+Import的三合一）

> ⚠️ 这是红方Q8/Q20的核心应对——如果PDF体验做不出来，果断转型，不硬撑。
